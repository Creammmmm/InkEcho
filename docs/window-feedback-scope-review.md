# 接收窗口反馈等待：当前实现与验证边界

2026-10-28 对当前未提交源码进行只读路径审查，并补充调度器离线回归。
用户要求恢复接收窗口帧同步等待设置、默认 40 ms；现有实现**不能证明该
要求在所有输出路径上完成**。尤其不能把绘制提示或任何等待写成目标已
处理、显示或呈现该字符。

| 输出路径 | 设置实际作用 | 边界 |
|---|---|---|
| 原生 Xorg 的 XTest 键盘 | `x11_mapping_wait_ms` 默认 40 ms，只用于首次以外的真实映射变更后等待；`x11_feedback_timeout_ms` 默认 40 ms，是 DRAW 提示等待动态超时下限 | 首次映射固定 100 ms；缓存复用不付映射等待。DRAW 只在可观察到目标 XSync 或 XDamage 时启用；提示可以提前释放，估算可能延长到 250 ms。它不是每字固定 40 ms，也不是呈现确认 |
| XWayland 的 X11 目标 | Hybrid 可以把同一任务快照传给 X11 后端的映射等待 | XWayland 映射仍需各目标独立验证；当前 X11 绘制反馈不会在该后端启用，反馈下限对该路径无效果 |
| 原生 Wayland 虚拟键盘 | 使用单请求 INPUT 往返延迟调度及独立映射/释放保护 | 这两项 X11 设置不参与；请求完成不是接收窗口绘制或呈现确认 |
| Fcitx5 / IBus 桥 | 走各自提交协议 | 这两项 X11 设置不参与；提交返回不能称作已呈现 |

Xorg DRAW 不可用或观察异常时降级 NONE；当没有映射变化且此前发过字，
NONE 模式另有 20 ms 保守复用间隔，不是用户配置的绘制超时。INPUT 的
动态调度基于请求往返数据，不消费 DRAW 提示；每个目标切换会使旧提示
代际失效。反馈下限和映射等待均于输出会话读取任务设置快照，修改从
下一次任务生效；Hybrid 跨后端保留 X11 的快照。设置页如实称为“X11
绘制反馈超时下限”，而非保证逐帧同步。

现有实桌面证据详见 `x11-mapping-wait-validation.md`：Ubuntu 24 Xorg 的
冻结源码和现有运行时对照记录了 40/80 ms 设置保存与会话读取、目标文本
准确性和输出总时间；该探针**没有观察逐字符绘制或帧呈现**，样本不能
证明 40 ms 会提升流畅度。它不是当前新包的完整验收。历史 r2/r3 包检查
确认默认值及部分输出，但不构成这项参数在双系统、所有桌面和各后端的
效果验收。

本次补充 `test_draw_feedback_timeout_is_a_floor_only_for_draw`：用确定
时钟在无提示、无新映射的单元模型中验证 40/80 ms 只改变 DRAW 超时，
NONE 为独立 20 ms 保守间隔、INPUT 不受该值影响；并非真实桌面计时。
`tests/test_output_pacing.py tests/test_keyboard.py tests/test_hybrid_keyboard.py
tests/test_x11_feedback.py tests/test_config.py` 共 253 项通过；指定的任务
设置快照和设置页保存测试 2 项通过。首次合并测试因错误地假定 NONE
无等待导致新增测试失败，修正为独立 20 ms 行为后通过；其余原始长测试
因未指定 Qt offscreen 运行环境被主动中止，不能计为通过。未改产品输出
逻辑；当前审查未发现设置传播明确错误。

后续如需真正面向当前接收窗口的帧级信息，必须先证明桌面协议能安全
提供与目标相关的可信信号，分别为 Xorg、XWayland、原生 Wayland 和
各输入法协议设计不依赖目标文本的可复现验证；不可将窗口无关的绘制、
提交回执或单次等待冒充逐字确认。无法获得信号时应明确退化能力，而非
假装已实现。还需验证真实目标逐字可见性、不同刷新率、取消/切焦与
双系统同一实际包；这些均不由上述离线测试证明。

## 原生 Wayland 信号与可落地范围

标准 [`wl_surface.frame`](https://wayland.freedesktop.org/docs/html/apa.html)
是表面拥有者为其自身表面请求的下一帧调度回调；不可见表面可能不收到。
[`presentation-time`](https://gitlab.freedesktop.org/wayland/wayland-protocols/-/blob/main/stable/presentation-time/presentation-time.xml)
的反馈关联具体表面的内容提交。二者既不让独立输入程序订阅任意目标
应用的表面，也不表示某次输入被目标处理；输入焦点切换时旧表面的事件
尤其不能作为新目标的证据。RemoteDesktop 输入接口亦不提供逐字的目标
帧确认。特定桌面的内部绘制事件未经证明与目标输入对应，不应当假装
是可移植的逐字确认。

隔离 Ubuntu 26 GNOME Wayland 的真实 Fcitx / GTK 目标对照见
`../experiments/fcitx-handoff/wayland-frame-hint/README.md`：暂停目标进程
时调用返回 0.507 ms，但经过 40 ms 目标仍未处理字符；恢复目标后才收到。
这是单个真实桌面样本，不是屏幕呈现测量，不能推断 IBus 或其他桌面的
具体时序。相关真实服务人为延迟、可取消 40 ms 上限的调度原型另见
`../experiments/fcitx-handoff/wayland-transport-pacing/README.md`，其中
正常、取消和自然切窗各有一次对照；它只能观察输入链路耗时，不能保证
目标处理或显示，也未证明提升用户体验。

可落地的选择是将可调值明确命名为输入发送节流预算而非帧同步，限定
在确有可测请求耗时的后端，仅作为可中断的调度策略，并在每次发送前
检查取消和截止、使用当时焦点、不重放结果不确定的字符。需先完成不同
真实负载、系统和后端的对照；当前不建议把它默认打开或称为已实现用户
要求。若将来由自愿配合的目标提供与其输入和表面提交关联的可信反馈，
可以设置 40 ms 等待上限：超时只代表未获得信号，切焦时丢弃旧信号，
而非视为处理成功。此类协议、授权及实际兼容性尚未验证。
