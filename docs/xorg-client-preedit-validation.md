# Xorg client and IBus composition investigation

On 2026-10-31, separate offline Ubuntu 24.04 GNOME Xorg and Ubuntu 26.04 XFCE Xorg QEMU snapshots exercised the automatic output route with synthetic recorder/provider input and self-owned targets. Both tests ran with an X11 session environment and selected the `_XTestDriver`. Ubuntu 24 logind active/x11 was observed in the tool output at the time, but that command was not saved independently; the current archive alone cannot verify the active state. Ubuntu 26 has a separately saved logind/Xorg session check. The runtime and dependencies came from the same old 0.15.0 AppImage, SHA-256 `94a73232871abaca8c91fb5f58e52059be404f10605955562d39bf31ec64354a`; the 94 regular files under `inkecho` were overlaid from the same `e80ea46` source snapshot and compared between the test share and guest copy. The source manifest excludes symlinks; its SHA-256 was `c6774a4e8d4d7f93b27037ed3ef615b7ade7f0c6e6b376237e47b2ca56729508`. This is not a final AppImage or release acceptance.

## Controlled observations

- Ubuntu 24 GNOME Terminal ran a self-owned raw-mode CLI receiver. A normal Session sent `甲乙丙丁abc123` and the receiver recorded all ten characters. In a separate run, the receiver process stopped itself after reading `甲`; the terminal emulator remained running, and after resuming the receiver it read the complete string. This tests a delayed CLI process behind a live terminal, not an unresponsive terminal emulator. Programmatic cancellation in another run left `甲` and Session reported one dispatched character. The terminal launcher exited 0 after the self-owned receiver was sent SIGTERM. Actual Codex CLI and Claude Code were not installed or tested.
- On both guests, Chrome 154.0.8037.97 opened a local synthetic page in a fresh profile without a sandbox-disabling command-line flag. In normal output the textarea recorded all ten characters. When the page changed focus to a second textarea after its first input event, the first received `甲` and the second received `乙丙丁abc123`. Cancellation left `甲`. These are controlled individual samples, not evidence for arbitrary websites or all focus timings.
- A separate cross-window sample on each guest switched focus with a test-only `xdotool` hook immediately after the first XTest key release. Chrome recorded `甲`; the second self-owned GTK window recorded `乙丙丁abc123` and was active and focused at the later sample. The GTK actor was sent SIGTERM and exited -15. This does not prove lossless delivery for other switch timings, clients or delayed event queues.
- **Both guests reproduced an IBus composition compatibility problem in Chrome.** With actual libpinyin active and `ni` entered by synthetic keys, the textarea observed `compositionstart` and `compositionupdate` ending in `你`. On the first simulated output character `甲`, the page recorded `compositionupdate` and `compositionend` for `甲`. The full-output sample then showed `甲乙丙丁abc123`; pressing space afterward produced `甲乙丙丁abc123你`. In the programmatic cancellation sample it showed `甲`, and space afterward produced `甲你`. Thus the previously composed candidate was still subsequently committed in these samples, but the page's composition event lifecycle was changed during injection. The results do not establish that all applications preserve or lose their pending composition, or that their event handlers remain correct.

On Ubuntu 24 the first Chrome composition fixture retained events across cases; it was corrected to clear them and rerun, and both runs remain in the local evidence. The first terminal run accidentally included cached Python files in the overlay, so it is retained separately and is not the final 94-file result. Ubuntu 26 initially had no global IBus engine; the first composition attempt stopped before input. After setting an isolated `xkb:us::eng` baseline and then selecting libpinyin, the independent run above succeeded. Ubuntu 26 lacked a browser in the snapshot, so 255 regular files of the locally installed Chrome program were copied to the guest and checked against a file-hash manifest; no user profile was copied. The guest comparison result was saved, but the comparison command itself appears only in the tool output, not a separately retained script. No terminal emulator or real coding CLI was available there, so no Ubuntu 26 terminal result is claimed.

## Detection boundary and cleanup

The Ubuntu 24 guest's IBus `InputContext` D-Bus introspection exposed preedit update/show/hide signals but no read-only property giving the already-active preedit state. This introspection was observed in tool output only and has no separately saved raw log, so the retained archive alone cannot independently verify it. Listening only after a task begins cannot prove that an earlier composition is absent, and those update signals contain text. Polling a non-XKB engine and refusing output would also block idle users; an asynchronous engine query and later XTest emission are not atomic. These observations do not establish a safe general detector. No product fallback or input-method behavior was changed in this investigation, and no uncertain text was retried.

The Ubuntu 24 guest removed six temporary libpinyin packages and restored the input source to `xkb:us::eng`. Its first engine query immediately after restarting IBus failed while the service was not ready; a later independent check returned `xkb:us::eng` and confirmed all six packages absent. The old runtime and shared directories were unmounted, and the guest shut down normally. Ubuntu 26 stopped the test-started IBus instance, removed the temporary browser and test profiles, restored the saved account session to Ubuntu Wayland, observed a new active Wayland session, unmounted the runtime and shares, and shut down. The old Xorg session was still closing at the recorded Wayland check; the restored GNOME session had started its own IBus daemon. Both containers exited 0 without OOM and the disposable snapshot archives were stream-verified. The 26 first no-engine failure and the 24 cleanup retry are retained in local logs.

To reproduce, use isolated guest snapshots with the referenced old runtime, frozen source and self-owned Chrome page/terminal receiver; the experimental launchers and raw evidence remain local under the task's `inkecho-xorg-clients` directory. Do not run the test keystrokes against a user's active desktop. These results do not cover actual Codex/Claude CLI, other browsers, physical keyboard shortcuts, audio, network providers, Xorg input across arbitrary clients or a package built from the current commit.
