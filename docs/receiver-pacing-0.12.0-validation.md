## 实际语义

UI 中的“接收窗口绘制提示等待上限”对应 `receiver_feedback_wait_ms`，默认 40，范围 20–250；通过实际 `ConfigStore` 保存、实际 `Session` 的读取器在下一次 `output_session` 创建时快照，并逐例核对保存值与快照相同。本轮没有操作设置页控件，不将配置 API 的验证冒充 UI 交互验收。

只有检测到原生 X11 DRAW 能力、已有未退役的发送窗口且预算耗尽时，才等待绘制提示；提示可能已经到达，也可能提前结束等待。实际超时上限取自“X11 自适应反馈基准”、已有延迟/抖动估计与该设置的较小值。它不是每字符固定睡眠，也不覆盖键盘映射及按下/释放的独立安全等待。超时只退役调度债务，不确认文字显示，也不重试已发送输入。

本轮的绘制提示是生产 `X11Feedback` 从真实 X11 counter / Damage 取得的通知，不是应用消费正文、逐字符渲染完成或屏幕呈现 ACK。窗口光标闪烁、装饰等也可能产生绘制变化，因此不能将通知与某个字符一一绑定。

## 测量方法

- 使用真实 GNOME Xorg 会话和两个专用 GTK3 TextView，`gtk-im-context-simple`，实际生产模拟键盘。未注入假反馈、未替换 sleep 或 clock，也未使用剪贴板。样本为重复 `a` 共八个字符，避免把反复键盘映射的等待混入观察；不以此宣称覆盖全部 Unicode/键位组合。
- 每例创建新的实际 `Session` / 输出会话。只观察式包装真实 `_send`、`OutputPacer.before_send` 和真实 `X11Feedback` callback，记录 `CLOCK_MONOTONIC` 纳秒、当前作用域/预算/提示状态、按键目标和收件窗口事件。包装回调继续调用原实现，不提供额外 credits。
- “有提示”目标正常绘制；“无提示”对照在目标已显示并获焦后调用该自有 GdkWindow 的 `freeze_updates()`，文本缓冲仍真实接收键盘，窗口表面暂停重绘。真实 DRAW 能力仍存在，但该固定目标实测提示数为 0。**这不是无反馈能力 NONE 降级测试**，不能用它证明“不支持反馈”的平台行为。
- 初始映射等待、按下/释放时长保留。表中时间是 eligible 且尚无 hint 的 `before_send` 进入至退出实测耗时；包含事件循环调度，约 0–1.2ms 的超时越界不是硬实时保证。每例延后复查接收文字不再增长，按下/释放数量一致。

## 默认基准 40ms 的结果

| 绘制上限设置 | 正常绘制实际提示数 | 冻结目标提示数 | 无提示等待范围 / 中位数（ms，7次） |
|---|---:|---:|---:|
| 20ms | 7 | 0 | 20.46–20.81 / 20.56 |
| 40ms | 8 | 0 | 40.22–41.10 / 40.87 |
| 80ms | 8 | 0 | 40.27–40.99 / 40.95 |

六例均收到精确八个字符、8 次按下和 8 次释放，延后无新增。正常绘制的 40/80ms 例在预算检查时提示已经到达，相关调用约 0.015–0.046ms 即返回；20ms 例有一次未及时获得提示，等待 20.53ms 后继续，其他相应调用约 0.012–0.027ms。这里不能解释为目标每字符都在这些时间内完成显示。

**80ms 没有把默认反馈基准 40ms 强行扩大为 80ms。** 该设置是等待的上限，而非最短或固定间隔，实际观测符合这一语义。

为单独观察三个上限，将另一个合法用户设置“X11 自适应反馈基准”固定为 250ms，其他生产行为保持不变，再对冻结目标测量：

| 绘制上限设置 | 实际提示数 | 无提示等待范围 / 中位数（ms，7次） |
|---|---:|---:|
| 20ms | 0 | 20.36–20.69 / 20.51 |
| 40ms | 0 | 40.16–41.19 / 40.93 |
| 80ms | 0 | 80.32–81.05 / 80.85 |

三例仍精确八字且按键平衡。这是用户可设置参数之间的受控对照，不是默认性能承诺，也没有改变生产 pacing 参数公式。

## 取消与切焦

独立 r2 对 20/40/80ms 均以反馈基准 250ms、旧目标冻结，在首个真实未获 hint 的预算等待进入 5ms 后发起操作。取消通过真实 asyncio task cancellation 与 task-validity 状态生效，不伪造输入完成。

- 三档取消均只收到首字 `a`，取消之后没有新的按下事件，按下/释放各一次；等待在约 5.17–5.19ms 时退出，无需等满 20/40/80ms，延后正文不增加。原始纳秒记录和取消到 wait-exit 延迟见 [summary.json](evidence/receiver-pacing-0.12.0-748856/summary.json)。首轮另一次 80ms 取消同样通过，单独保留，不作为新的参数组合计数。
- 三档切焦均继续发送总计八字，无取消、无重放、8 次按下/释放平衡。20ms：旧窗 `aa` / 新窗 `aaaaaa`；40/80ms：旧窗 `a` / 新窗 `aaaaaaa`。发起创建/激活新窗的请求不等于焦点已完成转移；20ms 那次在新窗获焦前仍有一字送到当时的旧光标，属于允许的当前光标语义。
- 新目标正常绘制，因此分别观察到 6/7/7 个真实新窗提示；旧冻结目标提示均为 0。作用域 token、按下事件目标 XID、新旧文本及时间顺序留在每例原始结果中。没有把旧提示当成新窗确认，也没有把焦点变化当成任务过期。

本轮检查的是各个真实按键发送机会的行为，不承诺 OS 窗口激活或用户取消在零时间内完成，不代表可以撤回已经发送的字符。

## 保留失败与限制

1. 同一 QEMU 第27次 SSH 尝试就绪，串口保留 networkd-wait-online 延迟；未重启客机掩盖。首次执行缺少本轮 9p 挂载，`guest.py` 不存在；随后只读诊断也因不存在的 `/mnt/frozen` 返回非零。原始顶层 JSON 均保留，之后显式挂只读输入和专用输出，才开始实际包检查。
2. 首轮九个普通对照和 80ms 取消已通过；切焦例错误地断言整个样本无提示，但新窗口正常绘制，真实获得七个新窗提示，故套件退出 1。该次失败与目标原始记录保留；驱动没有在断言失败前导出完整 observer rows，不能将其当完整通过样本。
3. 首轮独立 `Session` 驱动缺少 `QCoreApplication`，记录了 `QObject::startTimer ... event dispatcher ... destroyed`。r2 创建正常 QCoreApplication，再以独立新目录补齐三档取消/切焦，无该初始化警告；没有修补或改写首轮原始记录。
4. r2 区分旧冻结窗 0 提示与新窗有真实提示，六例完整通过。共保留 16 份成功原始 result（九普通、首轮一次取消、r2六例）和首轮一次切焦失败；没有把失败覆盖为通过。
5. 本轮只覆盖 Ubuntu24 GNOME46 **原生 X11** 的自有 GTK 目标，未扩展 Wayland、XWayland、Fcitx、IBus、浏览器或第三方应用绘制确认能力；没有运行真实麦克风/云端，也没有物理快捷键或 GUI 设置控件交互测试。既有正式包双系统报告的限制保持有效。
