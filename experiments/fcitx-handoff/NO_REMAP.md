# X11 existing-map experiment

XTEST accepts a physical keycode, not a Unicode character. The [XTEST protocol](https://xorg.freedesktop.org/archive/X11R7.6-RC1/doc/xextproto/xtest.html) defines this directly. The [GTK simple input context](https://docs.gtk.org/gtk4/class.IMContextSimple.html) documents Ctrl+Shift+U as an input method feature; that mechanism is outside this experiment's no-input-method fallback restriction and cannot be assumed in all applications.

On Ubuntu 26.04.1, XFCE, active X11 in an isolated QEMU desktop, an actual Fcitx bridge committed fixed `甲` into an owned GTK Fcitx entry. After focus moved to a separate GTK simple entry, a direct bridge attempt at `中` expired without a commit. The experimental client then used the current keymap's keycode for `b`, issuing one XTEST press and release. The entries contained `甲` and `b`, respectively. `XKeysymToKeycode` returned 56 for `b` and 0 for both `中` and `😀`. `xmodmap -pke` before and after had identical SHA-256 `39e6f5ca54e6b88038fd40cb6873adb456bc4abdc2273b40143659e0ee111ff7`.

The evidence is `build/handoff-review/no-remap/desktop26.log` (SHA-256 `e634a5364c6fdd9bc6f7db379a99bdfe8509fbcb777d8b6d7921a94d1b916521`). The experiment used the extracted r6 candidate AppImage SHA-256 `e4f2c6de3450cd997607baaeba41dd1764f8365c0bda73d9b9dd7c4ac395db54`, overlaid with `fcitx5.py` SHA-256 `8cd26a449056d65d9d08cb1c087c26a4d29c00bf8108a4d6f408ff7b2a28494e` and `output_router.py` SHA-256 `7dda79e409540f7950c708041649ecc108b54a369814f95edd6b7c486cf8a26c`. The product router was not used to perform the experimental handoff. No clipboard, real user text, actual microphone, or real external services were used. The test service and settings were cleaned up; the guest's account configuration was restored and compared, and the VM exited 0.

For reproduction, in an isolated X11 guest prepare `/tmp/handoff-r7/` as in `docs/automatic-framework-detection-research.md` and place this directory's `run-no-remap.sh` there. Copy `no_remap.py` to `/tmp/handoff-r7/no-remap.py`, then run `bash /tmp/handoff-r7/run-no-remap.sh`. The exact original probe used in the test is retained as `build/handoff-review/no-remap/probe.py`, SHA-256 `05055eb989c2296fd871ac7b80cb02cf5acf8929d1e0a1a12787ddea1f588aa9`; the versioned Python script was formatted after that run, SHA-256 `ebc3f58c8884b2eb1f7bca7b08e08e69c62b12ecce4f0c4f0f74ec074995aeb0`, and has not been rerun. The run script is unchanged, SHA-256 `3ab40559d50e847ddaf86ae896549ae4c7a103264cac7a2aac27c734713320d8`.

This demonstrates an ASCII-only possibility for one existing layout and one controlled receiver. It does not establish safe ordering after an arbitrary slow receiver, general Unicode support, actual framework auto-selection, production fallback, other layouts or systems, or AppImage release acceptance. It must not replace the current conservative partial-output protection.
