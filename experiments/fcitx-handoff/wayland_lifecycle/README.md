# Native Wayland keyboard mapping and controlled Fcitx handoff

On an isolated Ubuntu 26.04.1 GNOME Wayland session, a fixed GTK 3 native Wayland simple entry was focused and then paused with `SIGSTOP`. The extracted r6 AppImage's `WaylandKeyboardInput` emitted either `甲乙` or ten distinct characters `甲乙丙丁戊己庚辛壬癸` while the target was paused. In `held` mode the target resumed before output-session cleanup; in `early` mode it resumed only after session cleanup restored the keymap. All four samples returned exact expected text. This does not rely on a drawing event or claim that the keyboard method's return acknowledges the target. Raw results: `build/handoff-review/wayland-lifecycle/desktop26.log` SHA-256 `5b99dd0373bb6bcabcb29ac5313944f32fbe79e88a11431d06416462ff2ea6ba`, and `desktop26-multi.log` SHA-256 `c2ed49e8ca8d71803896abfc6824ddf87606fe0939e3dc701704b75c5d1e604b`.

A separate controlled cross-framework probe used real Fcitx and two owned native GTK entries. Fcitx committed `甲` to its own entry; the simple entry then obtained focus, and the Fcitx bridge waited until its deadline with one accepted character and no uncertain delivery. The experiment manually passed only the known-unsent `乙丙丁戊己庚辛壬癸` to `WaylandKeyboardInput` while the simple target was paused. After the keyboard output session and mapping cleanup completed, the target was resumed: its entry contained that exact suffix and the Fcitx entry contained `甲`. Raw `cross26.log` SHA-256 `344423b0b4ee43efab4c2dbe34b332df288047250f8c01c0d64b99056567856d`. This probe manually coordinates backends; **the production OutputRouter still blocks this partial-output handoff**.

The base r6 candidate AppImage SHA-256 is `e4f2c6de3450cd997607baaeba41dd1764f8365c0bda73d9b9dd7c4ac395db54`. Its extracted `wayland_worker.py` SHA-256 is `74c9693b6d83f0c8f4fa7e529c5b9c1ef7930e2be002dfca5d233247b07de39e`, and `wayland_keyboard.py` is `bd76f5d8bb972fce9a7c3bd0dcbfc44fc61f128ab3e6b27bbe7415da4eff29bf`; these were independently checked in the AppImage with `unsquashfs -offset 944632 -cat`. Reproduce only in a disposable Ubuntu 26 GNOME Wayland guest with GTK 3, Fcitx 5, and the package's normal backend requirements: copy the raw probes, target scripts, r6 AppImage, `run-cross.sh`, and the pinned `fcitx5.py` into `/tmp/wayland-lifecycle/`. Extract the AppImage there. Export the guest's `DISPLAY`, `WAYLAND_DISPLAY`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`, `XDG_SESSION_TYPE`, `XDG_CURRENT_DESKTOP`, and `XAUTHORITY`, along with package `APPDIR`, `PYTHONHOME`, `PYTHONPATH`, and `LD_LIBRARY_PATH`. Run its bundled Python with `probe.py held`, `probe.py early`, and the corresponding `probe-multi.py` modes. `bash /tmp/wayland-lifecycle/run-cross.sh` separately creates the private Fcitx service and runs the cross probe, restoring its environment. These scripts manipulate the test desktop and must never run on a real user desktop.

The samples suggest native Wayland event ordering deserves further investigation, but do not prove protocol guarantees for arbitrary clients, queued focus changes, cancellation, XWayland, Ubuntu 24 GNOME 46, any non-BMP character, or production auto-routing. Existing direct `NotifyKeyboardKeysym` cannot encode arbitrary missing keysyms on Mutter; see `docs/current-cursor-input-validation.md`. No package acceptance or release claim follows from this experiment.
