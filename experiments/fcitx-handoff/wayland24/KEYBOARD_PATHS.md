# GNOME 46 native Wayland Unicode keyboard path investigation

The current production keyboard backend requires Mutter's `SetKeymap` and `KeymapCapabilities`; the Ubuntu 24.04.5 GNOME 46 Wayland guest returned `unsupported_compositor` during direct preflight. The corrected parent-backend diagnostic and its source-overlay retest are recorded in `README.md`. This does not exclude future compositor versions or other independently verifiable mechanisms.

The [official RemoteDesktop portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html) offers a user-authorized keyboard session via keycode, keysym or EIS; the portal's standard `Start` dialog is required. The [EI keyboard protocol](https://libinput.pages.freedesktop.org/libei/interfaces/ei_keyboard/index.html) sends keycodes and reports a server-provided device keymap that is constant for that device's lifetime; a sender must select codes appropriate to that keymap. These facts alone do not establish arbitrary Unicode support. Earlier isolated native Wayland keysym observations and Mutter source analysis are in `docs/current-cursor-input-validation.md` and `docs/ubuntu24-experience-repair.md`; they must not be generalized to every version or backend.

A new read-only registry probe on the actual Ubuntu 24.04.5 GNOME Wayland QEMU guest showed that `zwp_virtual_keyboard_manager_v1` was not advertised to an ordinary client. Output `build/handoff-review/wayland24-r3-registry.log` has SHA-256 `77f306abad35482d7219475429a1026771a3c1528558c85bd7fe9bdb089f0951`; it created no input or clipboard objects. The absence of an advertised interface does not prove no privileged or differently filtered interface exists. The versioned protocol's [virtual keyboard specification](https://gitlab.freedesktop.org/wlroots/wlr-protocols/-/blob/master/unstable/virtual-keyboard-unstable-v1.xml) permits supplying a keymap where a compositor offers and authorizes it, but this guest did not expose it to the probe.

The historical keyboard-only portal probe was launched twice in the isolated guest, with an unpersisted portal session and an owned GTK fixture planned after consent. Both attempts timed out at the standard keyboard authorization dialog; neither obtained a grant or sent any text. The original logs are `build/handoff-review/wayland24-r3-portal.log` SHA-256 `4eef9cdcccfcac01dc033fbb3342dc353e779d5b3aa7a358eb42f0d7bf911095`, and `wayland24-r3-portal-r2.log` SHA-256 `48668eae014b3cc8051e670ac0ea680d1685edee073fd15ce6a1b13458e23624`. The retained screenshot `wayland24-r3-consent.png` SHA-256 `674a949e5ea39909982901b4965ff0d15c92415f487bea208af7d4a598b230b2` shows the standard remote-interaction switch; attempted QMP input did not produce an observed authorization before the deadline. **These are inconclusive consent failures, not Unicode-delivery failures.** No workaround bypassed the portal or used the clipboard.

In a subsequent isolated investigation, two more bounded authorization attempts timed out without text being sent: `build/handoff-review/wayland24-r4-portal.log` SHA-256 `10e7fe95f8c43ec7f36f089a9f24dac155fea1076c0f34ecdec2fabf910aef27` and `wayland24-r4-portal-r2.log` SHA-256 `ba253c9efb2ed7b7cedd9a7b22775d926768602cb78bdd0f95756dcfab996412`. ### Completed standard authorization and keysym control

A later isolated Ubuntu 24.04.5 GNOME Wayland run inspected only the `Remote Desktop` frame belonging to `xdg-desktop-portal-gnome`. The dialog exposed an `Allow Remote Interaction` **check box** with the `toggle` action and a `Share` **push button** with the `click` action. The probe invoked those two standard actions after checking the unique name, role and action; it did not invoke any clipboard actions. The portal returned `keyboard_only_granted=true`, so this experiment reached the actual Unicode test without bypassing authorization. This establishes a working authorized route for the test harness; it does not establish the precise reason earlier QMP/VNC attempts timed out.

The owned native GTK fixture received 15 of the 28 fixed sample code points: ` InkEcho caf  \n`. The ASCII letters and spaces and the newline were the positive control; Chinese, `é`, `Ω`, `😀`, and Chinese punctuation were not delivered. The test intentionally exited with `Owned fixture Unicode mismatch`. This is a **negative Unicode result for the measured portal keysym route**, not a claim that every conceivable portal or input backend fails. The input was synthetic; no real user document, microphone, cloud service, clipboard operation or system input-method registration was involved.

No reliable generic GNOME 46 Unicode keyboard implementation has been established. This investigation is not AppImage acceptance and does not justify silently modifying system input methods, claiming native Wayland compatibility, or disabling the existing conservative fallback protection.
