# IBus extension pre-dispatch negative result: isolated protocol model

The existing candidate extension obtains GNOME Shell's IBus panel and calls `commit_text`. It maps a missing panel and exceptions to `unknown`; this is conservative but does not distinguish the narrow condition where the extension itself observes no panel before making any submission. This experiment models a possible protocol distinction without modifying IBus, GNOME, a user session or the product. It does **not** identify whether a focused text target exists and cannot justify enabling automatic IBus selection.

In this model, resolving the panel yields either a callable or no service, synchronously before the call. Missing service fails the gate and returns `no_service` plus prior attempts; an actual call, including one that throws, is attempted/unknown. A caller may consider keyboard fallback only upon an authenticated, correctly sequenced `no_service` response with both local and server prior-attempt counts zero and a still-active task. An absent reply, timeout, owner change, malformed reply, prior attempt, cancellation or any exception after dispatch must be unknown/stop and never replay. The model `route` deliberately omits authentication and active-task checks and must not be used in production.

`node test.mjs` exercises no-service before dispatch, gate closure, single-use setup, attempted prefix followed by no-service, missing response, post-call exception, and cancellation; stdout is `test.log`. No D-Bus transport, GNOME Shell, IBus, authentication, real event ordering, target focus, task deadline or desktop is tested. In production, the extension would have to use its already authenticated unique sender/session capability, `resolve()` would have to be side-effect-free, and every protocol result must be verified against the pinned owner. A no-service response may be lost after being sent; the caller must not infer it from a timeout. Cross-version compatibility, cancellation races, errors during serialization, and real 24/26 shell tests remain unverified.

This is a design-only experiment; it does not change packaged files or assert the current extension implements the new result. Supporting it would require versioning the protocol, updating its hashes/installer, output router and extensive tests. It would improve handling only when the panel is actually absent. Existing inability to distinguish a live target from the fake IBus context remains, so auto IBus is not supported on this evidence.
