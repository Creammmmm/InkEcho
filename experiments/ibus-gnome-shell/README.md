# IBus GNOME Shell communication prototype

This isolated prototype is not integrated into InkEcho, not automatically enabled, and not evidence of support. It uses the Shell's current private `_panelService` and calls its `commit_text` without selecting or changing an IBus engine. The extension never logs text, queries surrounding text or stores a target; the panel is looked up afresh for each scalar. The Shell/IBus focus path is not an acknowledgement that the target received or displayed text.

## Protocol and trust

The client creates one random 256-bit capability in an exclusive no-follow mode-0600 file under an owner-only runtime directory. The Shell opens it with O_NOFOLLOW and checks owner, mode, regular-file type and token from the same held descriptor. Begin binds the D-Bus unique sender and token; Commit requires the same sender, token, one scalar and exactly the next sequence. Cancel invalidates locally before sending the server request. Owner loss invalidates the server session; tokens cannot be reused during the extension lifetime, bounded to 1024 sessions in this prototype. A new task requires a new token and bus connection. Controls are rejected; newline/terminal semantics remain undesigned. Any attempted but unconfirmed delivery is `unknown`, permanently fails that task and must not be replayed. `attempted` is only a panel call, not end-to-end receipt. An already queued D-Bus call cannot be retracted.

This is an explicit access gate, not a strong boundary against other processes running as the same UID: such processes may read or alter the runtime file. The client checks the service owner UID and PID and requires a root-owned `/usr/bin/gnome-shell` executable before sending the token, then pins that unique bus owner. Same-UID writers can still alter a held file, and the owner/sender authorization policy and file cleanup after crashes require independent review. Do not ship this code, enable it on the host, or make security claims before that review. The per-extension token set needs a production lifecycle without replay or exhaustion.

## Test results

From the repository root, run `node experiments/ibus-gnome-shell/gate.test.mjs`, `.venv/bin/pytest -q experiments/ibus-gnome-shell/test_client.py`, and `bash experiments/ibus-gnome-shell/run_capability_test.sh`: gate checks passed; 6 fake-bus/client tests passed; GJS descriptor checks passed. The GJS compatibility layer may print a deprecation warning for `Gio.UnixInputStream`. These tests cover sender/capability mismatch, token reuse, ordered fragments, cancel, owner loss, in-flight cancellation, timeout/no replay and safe capability-file cleanup. Those unit tests do not execute the extension in GNOME Shell; the later virtual-desktop trial below does.

Previous separate synthetic-only Shell probe, which did not implement this protocol, ran in an isolated Ubuntu 26.04 / GNOME 50.1 guest: two GTK entries received Chinese in turn with the libpinyin engine name unchanged; see `earlier-probe.md`. It only canceled a locally queued third send, not an in-flight request. GNOME 46 source includes the same private field but has not been tested. At that stage no candidate extension or cross-window trial had been run; see the later trial below. Actual package, Ubuntu 24.04, browser, terminal, preedit, multi-seat and restart support remain unestablished.

## Isolated desktop retest plan

1. Use a separately owned isolated VM snapshot; record session type, GNOME/IBus versions, prior input sources, engine, enabled extensions and installed packages. Install the prototype extension only there. Create a private capability file and start a client on its own session D-Bus; do not mount host desktop sockets, credentials or config.
2. Verify wrong sender, wrong token, replaced file, repeated token, replayed sequence and owner disconnect are rejected. Exercise crash, extension disable/restart and safe cleanup; verify two simultaneous clients cannot steal an active task. Check whether a same-UID process can read the capability and report the result, not a claimed security guarantee.
3. With an existing non-XKB engine and preedit state, use two owned windows and widgets, a browser and terminal. Confirm current-focus delivery, focus switching during output, mixed Unicode, unchanged engine and any preedit side effects; test no focused client and multiple input contexts. Do not read surrounding text.
4. Cancel before Begin, between characters and while Commit is pending, then deliver delayed replies. Confirm unsent calls stop, queued calls are reported ambiguous, and no backend replays them. Also test bridge death and Shell/IBus reconnect.
5. Repeat separately on Ubuntu 24.04 GNOME 46 and 26.04 GNOME 50, Wayland and Xorg, then test the same candidate package on both systems if release scope includes it. Capture exact versions, steps, artifact hash, results and limits. Finally restore input sources, extension list and packages; remove temporary data and shut down the owned VM normally.

## Descriptor and private bus follow-up

The Shell prototype now opens the file with Linux O_NOFOLLOW|O_NONBLOCK|O_CLOEXEC, checks type/owner/mode/size through the still-open descriptor and reads the token from that same descriptor. Standalone GJS checks: valid regular mode-0600 token accepted, a symlink and a mode-0644 file rejected. A same-UID writer may still alter the file or interfere with Shell, so no same-user security boundary is claimed.

`bash experiments/ibus-gnome-shell/run_isolated_bus.sh` created an independent D-Bus and ran an actual GJS receiver plus Python client: wrong unique sender with the valid token was rejected, ordered commits and cancellation succeeded, and the file was cleaned. This private probe explicitly skips Shell process owner verification and has a fake delivery callback; it is neither an actual Shell/IBus test nor real target delivery. The client separately checks UID/PID and root-owned GNOME Shell executable before revealing a token; a fake-owner unit test verifies no token is sent to a rejected owner. Full tests: six Python tests plus JS gate checks pass. At that point real Shell protocol and cross-window checks remained pending; later 26.04 results are recorded below. Dual-VM and lifecycle checks remain pending.

## 2026-10-28 actual GNOME 50.1 protocol trial

In a disposable Ubuntu 26.04.1 Wayland guest, temporarily installed the candidate extension and dependencies, selected libpinyin, and ran `guest_protocol_test.py` in two distinct owned GTK3 windows. The actual extension zip was SHA-256 `6a6d15fed81cfae103af5226a2794710dec83a8ad693fde845be7a294328401b`; client `1198e83f24a4fbf2855f85dbed43dd2e154209d2579d7f7b586c7f36dde8d799`, guest test `a78e031bb6625f0440a87ed0079aa40a03215425d637d675cef0e2a87b4e6616`. Output `ubuntu26-protocol-result.json` records A=甲, B=乙丙, libpinyin unchanged, foreign unique sender with same token rejected, cancellation before next send stopped, and cancellation after server processed the previous send while the client held its reply did not send the second character. The previously sent 丙 remained. The latter test does not delay processing inside Shell and does not prove an already queued D-Bus request can be retracted. This is virtual-desktop evidence, not real hardware or an AppImage.

Afterward restored `enabled-extensions` to empty, `sources` to xkb/us and engine to xkb/us; extension uninstalled, service owner absent, capability file absent, guest files removed, 10 temporary packages removed, and QMP normal powerdown returned 0. Downloaded package cache and package-manager history remain in the disposable guest. Earlier synthetic-only probe and its first-run error remain recorded separately in `earlier-probe.md`.

Initially the 24.04 VM had not reached the desktop: initial boot and one retry each hung in early boot and SSH banner timed out. A later boot succeeded; see the subsequent trial below. Both QMP screenshots are saved as `ubuntu24-first-boot.png` and `ubuntu24-retry-boot.png`. The first QMP shutdown exited 0; after the second QMP shutdown failed to finish within 20 seconds, the explicitly identified project-owned container was bounded-stopped and exited 0 (container signal, not a normal guest shutdown). No candidate files or settings were installed during those initial failures. At that stage GNOME 46 remained unverified; the later Xorg trial below is separate. Actual Ubuntu 24/26 packages, browsers/terminals, live microphone, IM composition, delayed server processing, stronger same-UID authorization and the full product integration remain unverified.


## Subsequent Ubuntu 24.04 Xorg protocol trial

After allowing approximately 125 seconds for the guest network startup timeout, the isolated VM reached GNOME Shell 46.0 on Xorg, with IBus 1.5.29, GTK3 and `xkb:us::eng`. The same candidate extension archive (`6a6d15fed81cfae103af5226a2794710dec83a8ad693fde845be7a294328401b`) and client were used. Two initial attempts failed before sending any text because the first owned test window was not active; the second attempt tried X11 activation before the window manager had mapped the windows. The test was updated to wait for mapping before activating the owned X11 window. Its SHA-256 was `41c7395a16b22f2105df8c8c7ed244d080f078a1b5cc99c32e9c47a49844384a`.

The corrected trial produced `ubuntu24-protocol-result.json`: the two owned GTK3 windows received 甲 and 乙丙, the original xkb engine name remained unchanged, a different D-Bus unique sender was rejected, cancellation prevented the next send, and cancellation while the client intentionally held an already-processed reply did not send the second character. The already-delivered 丙 remained. This does not prove cancellation can retract an in-flight request, nor does it validate a non-XKB input engine, Ubuntu 24 Wayland, browser, terminal, or actual AppImage. The 24 and 26 trials used the same candidate extension and client but different test-script revisions, recorded by their respective hashes.

Afterward the guest restored empty enabled-extensions, xkb/us input sources and xkb:us::eng; the extension was disabled and uninstalled, temporary files and capability were removed, and the service owner was absent. No guest packages were installed in this trial. The guest then shut down normally via QMP and exited 0.
