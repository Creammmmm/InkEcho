# IBus X11: XTest and XSendEvent comparison

On 2026-10-31 a separate Ubuntu 24.04.5 GNOME X11 QEMU guest ran without external network, using a disposable RAM-backed writable disk, read-only base images and self-owned Chrome and GTK targets. The guest used libpinyin, synthetically typed `ni`, and produced only fixed synthetic text; it did not interact with the host's input method or clipboard. `loginctl` reported the guest session active and X11. A 0.15.0 AppImage runtime (SHA-256 `94a73232871abaca8c91fb5f58e52059be404f10605955562d39bf31ec64354a`) was combined with the same 94-file source overlay as the earlier Xorg client investigation; this is neither the current source nor a packaged release acceptance.

The two methods exercise actual `Session` and automatic router with a synthetic recorder and provider. `_XTestDriver` is the tested old Xorg factory; `_XDriver` is explicitly constructed for XSendEvent and is **not** the production factory. Both were used with the same focused target and engine. Each listed row is one controlled observation, not evidence across arbitrary apps, drivers, windows, or focus races.

- In Chrome's self-owned textarea, both drivers delivered `甲乙丙丁abc123` while libpinyin was composing `你`; both also caused the page to observe `compositionupdate(甲)` followed by `compositionend(甲)` at the first output. A following synthetic space appended the original candidate `你`. This prevents recommending XSendEvent as a general solution for preserving Chrome composition. Chrome had an X11 environment and explicit `--ozone-platform=x11`; this is a local page, not an arbitrary real website.
- In the self-owned GTK3 X11 entry with `GTK_IM_MODULE=ibus`, both drivers delivered the ten-character sample with no composition, and while `preedit=你` remained visible before and after output. A subsequent synthetic space yielded `甲乙丙丁abc123你` and empty preedit. The GTK observation is different from the Chrome DOM lifecycle observation; neither implies general behavior.
- In a follow-up Chrome run and the GTK run, an async watcher sampled only the owned target's synthetic contents; once it saw `甲`, it requested programmatic cancellation. Both drivers left only `甲` in the sampled target after 1.3 seconds. In-flight events and other cancellation timings remain unproven. This is not physical ESC testing.
- In the initial Chrome XSendEvent cancellation sample, cancellation was issued at the sender's first-sent callback before the page received a character; the page still contained the composition `你`. It is retained in `browser-initial.json` and does not establish receiver-confirmed cancellation. The corrected follow-up is `browser-confirmed-cancel.json`.

Files `browser-compare.py.txt`, `gtk-compare.py.txt` and `session-probe.py.txt` are the exact guest-side source inputs for the follow-up. They additionally require the prior guest harness, verified old runtime, source overlay, PySide6/websockets, offline libpinyin packages, and Chrome. Do not run the fixture against a user's desktop. No cross-window switching, Ubuntu 26, physical keyboard, microphone, cloud transcription, or current AppImage was tested here.

The final GTK report records `sources_after` as `[('xkb', 'us')]`; it does not independently record the final engine after that run. The earlier Chrome reports record both that source and engine `xkb:us::eng` after their own runs, but do not establish the post-GTK engine. The guest-side package-removal output is retained in `remove-final.log`; it lists the six removals but contains no independent final package query. `fuse-cleanup.json` records that the runtime mount was gone. The subsequent shared-directory unmount and container status were observed during execution but their raw command output was not saved; they are not independently proved by the disk archive. QEMU exited 0 as recorded in `qemu-exit.json`; container exit 0, no OOM and removal were observed during execution. `archive.json` records only that the disposable disk archive was fully stream-verified; it does not prove guest cleanup or engine state. This isolated cleanup did not modify the host input method.
