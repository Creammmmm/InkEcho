# Ubuntu 24 X11 DRAW-to-NONE investigation

2026-10-29; candidate AppImage SHA-256 `6d537689d5e30f4611f1e8376025705bf5fcc26c9198c9cda7c51717d434e34a`, unchanged package extraction. Ubuntu 24.04.5 GNOME X11, active and unlocked, independent QEMU snapshot; original guest disk and backing images read-only, no real credentials, no host desktop, no external network. Test-only Fcitx and GTK input contexts; 16 fixed synthetic characters, not real recording or cloud ASR. See `inventory.log` and hash check in run logs. Container stopped and removed after tests.

A prior isolated 80 ms sample (`experiments/candidate-6d-feedback-x11/ubuntu24/output.log`) showed DRAW→NONE after three timeouts, but it did not record capability or focus reasons; its actual cause cannot be recovered from that log. To investigate without changing the candidate, `sender.py` wraps its pacer, X11Feedback `_degrade`/`poll`, and KeyboardInput `_bind_pacer`/`_disable_feedback` in the probe process only. These record capability reason, focus revision and pacing binds; two groups compare unmodified observation with deliberately suppressed DRAW hints. This instrumentation itself changes timing.

`output.log` contains six natural-observation and six hint-suppression samples. All twelve received the exact 16 characters, selected `counter_and_damage`/DRAW, and no mid-output downgrade or focus revision was observed. `disable_feedback` at the end is normal session cleanup, not a mid-output failure. No reproduction means the original unexplained event remains unexplained; twelve small synthetic samples cannot prove the issue absent.

`focus.log` is a separate controlled switch: sender was paused after one character, the second GTK control was focused, and sender resumed with hint suppression active. It records `feedback_degrade event_backlog`, focus revision 0→2, observer disable, and rebinding to NONE; first and second controls received 1+15 characters, matching the transcript. Per `src/inkecho/platform/x11_feedback.py`, the event queue remains nonempty after a maximum 64-event batch and the code deliberately drops the observation instead of risking a stale focus hint. The separate observation is consistent with the designed conservative fallback, not proof the earlier sample had that cause. It can reduce responsiveness during that output task; no evidence here establishes a correctness defect or justifies weakening the focus/backlog guard.

`unit.log`: 116 tests passed from an independent current-source copy (`tests/test_x11_feedback.py tests/test_keyboard.py`), including synthetic backlog, stale-focus invalidation and cleanup tests; it is not a desktop event test. No product code was changed as a result of this investigation.

Reproduce only on an isolated matching GNOME X11 guest: place the exact candidate in `/tmp/inkecho-r4-test/` and the included `sender.py`, `target-focus.py`, `run.sh`, `focus-run.sh` in its `probes/`. Confirm actual graphical session X11, active and unlocked. From that directory run `bash probes/run.sh <full-sha256> x11`, then `bash probes/focus-run.sh <full-sha256> x11`. Scripts assume UID 1000/session bus and DISPLAY=:0, start private Fcitx and change test session environment; do not run on a user's real desktop. The fake `probe-key` is not a credential. No physical Esc, real input, real application, frame presentation, or all focus/event races were verified; this is targeted evidence, not package acceptance.

The archived Python probe files have a `.py.txt` suffix to preserve their exact executed bytes. When copying them to the isolated guest, remove the final `.txt` suffix so the original shell scripts find their expected `.py` filenames. Do not edit the scripts or historical logs.
