# IBus GetEngine ownership and focused-context race on Ubuntu 26.04

An independent Ubuntu 26.04.1 GNOME Wayland QEMU `-snapshot` guest ran with original guest disk and base image mounted read-only, a read-only 9p input share and no external networking. All GTK widgets were created by these scripts; no text was sent or read and no clipboard or external user information was accessed. The guest's initial input source and engine were xkb US. To test the second engine only the disposable guest input source was changed to libpinyin; it was restored to xkb US before normal shutdown (`restore.log`). Docker wait returned 0, the container and temporary VM SSH key were removed, and the original disk was not modified.

Hypothesis: the documented read-only IBus `InputContext.GetEngine` might distinguish a genuine focused entry from the fake context used for a non-text button, without retrieving surrounding text. The [IBus API](https://ibus.github.io/docs/ibus-1.5/IBusInputContext.html) describes it as an engine-description query; [upstream implementation](https://github.com/ibus/ibus/blob/main/bus/inputcontext.c) serializes an engine description and restricts InputContext method calls to the owning connection. This is source review of upstream main, not independent proof of every installed version.

`run.log` and `run-r2.log` show real native Wayland and XWayland GTK3 entry controls and buttons, each with active window and focused widget confirmed. In each entry's own process, querying its current IBus context returned an engine description. A button's current path was the internal context and its query timed out after 2 seconds (`G_IO_ERROR_TIMED_OUT`), not a definitive no-target response. The first run omitted the precise error details; the second added them. The same entry engine-description digest was observed across its four xkb cases. Each actor's initial code is saved as `actor-first.py.txt`, the detailed-error revision as `actor.py.txt`; the first actual hash is recorded in the first log.

This apparent distinction does **not** work for an independent input application. `cross-xkb.log` shows that a separate observer process queried the same currently focused real entry context while the original GTK entry remained alive, and timed out after 1.5 seconds; the button context also timed out. The target process's same-context query had succeeded. `cross-libpinyin-r2.log` confirms the same pattern with libpinyin selected and verified in the isolated guest. The earlier `cross-libpinyin.log` is retained: malformed shell quoting prevented the source change, so it actually ran on xkb and is not libpinyin evidence.

`race-libpinyin.log` is a controlled own-process focus-change sample: the script records the IBus path while its GTK entry has focus, focuses its GTK button, verifies that the button window and widget are focused and records the new current path. Querying the old entry path still returns an engine description. That is a stale-context counterexample to assuming a successful query reflects current focus. No submission is made. One sample does not establish frequency or delivery behavior under every compositor schedule.

Scripts are exact bytes saved with `.txt` suffixes. To reproduce only inside a disposable Ubuntu GNOME guest, copy them without `.txt` onto a read-only 9p share `inkecho_input` and execute `run.sh`, `cross.sh`, and `libpinyin.sh` in order within the isolated graphical-session environment. `libpinyin.sh` expects the cross script copied to `/tmp/ibus-cross.sh`, and refuses to run the comparison unless `ibus engine` reports libpinyin. The focus race is `GDK_BACKEND=wayland GTK_IM_MODULE=ibus /usr/bin/python3 race.py` with the same graphical-session variables as `cross.sh`; `restore.sh` restores the recorded input source and shuts down the disposable guest. Script hashes and raw output permit verification; do not run them in an ordinary user session.

The evidence rules out this candidate as a safe universal cross-application detection mechanism for the tested version and engines; it does not prove that every IBus version or potential interface is unsuitable. Neither a successful query nor a timeout is delivery acknowledgement, and no automatic IBus routing or product code is enabled from this probe.
