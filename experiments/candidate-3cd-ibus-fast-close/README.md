Normal IBus case: GTK target received eight characters; Session reports `ibus_delivery_unknown` because IBus does not acknowledge target delivery. For `no_service_double` the same Session starts a second task as soon as the first becomes non-pending. Both real extension responses, authenticated against the pinned shell owner, were no_service with zero IBus commits; both locally disconnect and each keyboard fallback delivered the eight synthetic characters. Receiver contained exactly the concatenated 16 characters. `fast_close_begin/end` log monotonic seconds: on 24 they took about 0.202 and 0.176 ms; on 26 about 0.222 and 0.209 ms. Instrumented outgoing calls record no Cancel in either confirmed-no-service path, and a new Begin appears for the second task. Timings measure the local disconnect in these isolated samples, not total end-to-end latency. The generic Fcitx-oriented probe `passed` field is intentionally false for these IBus and two-task samples; verify the raw per-event sequence and target bytes instead.

For simulated reply loss the client raises after the first real attempted response; the target received one character, returned delivery_unknown and did not fall back or replay. This is not actual wire loss or a real daemon crash. Test target is a GTK fixture, not real speech, provider, CLI, every app, or all exception/cleanup paths; the later cleanup-exception fix needs a rebuilt candidate and separate verification. No full two-system package/release acceptance is claimed.
