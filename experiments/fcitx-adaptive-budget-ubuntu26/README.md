# Fcitx5 40 ms adaptive transport budget: Ubuntu 26.04

This is a design experiment, not a product patch or release acceptance. Ubuntu 26.04.1 GNOME native Wayland ran in a network-isolated QEMU `-snapshot` guest with read-only original disk, base image, and input share. The unmodified extracted candidate AppImage version 0.10.2 SHA-256 `207b97eb667e5439137b51963a2aa09515c7ba50a83496d9c10070e989252685` provided the real Python Fcitx bridge and native service. The test script wraps its D-Bus calls; it uses a separately launched test Fcitx service, owned GTK3 text controls, and 100 fixed synthetic characters. No user text, real microphone, cloud API or clipboard is used. The test runner restores its recorded user-service environment and stops its Fcitx process; the guest shut down normally with Docker wait 0 and its temporary snapshot and SSH test key were removed.

The prototype is adapted from `../fcitx-handoff/wayland-transport-pacing/`: it observes request RTT, computes excess above `max(2 × baseline, baseline + 10 ms)`, caps the next wait at 40 ms and decays the wait by 0.75 on later calls; the wait is cancellable. It measures transport behavior, not window processing or frames. For artificial-delay cases only, it pauses its own Fcitx process for 80 ms at the seventh request. The timing `duration_ms` spans `bridge.insert()` itself and includes the artificial pause where applicable; it does not measure frame presentation. Every test waits a further 1.2 seconds to check owned target contents.

| Scenario | Sample durations (ms) | Observation |
|---|---|---|
| Normal baseline, three runs | 39.607, 33.555, 34.505 | Each accepted and delivered 100/100 synthetic characters exactly. |
| Normal adaptive, three runs | 40.744, 33.816, 33.329 | Each accepted and delivered 100/100 exactly; no extra pacing wait occurred. |
| 80 ms service pause, baseline, three runs | 108.185, 114.439, 122.145 | Each delivered 100/100 exactly. |
| 80 ms service pause, adaptive, three runs | 331.637, 320.413, 320.819 | Each delivered 100/100; summed added waits 184.814, 184.094, 184.729 ms. Longest individual wall wait 40.138–40.188 ms due to scheduling. |
| Adaptive cancellation during pause-induced wait | 93.842 | Seven-character correct prefix; cancellation woke wait after 10.118 ms; no further character observed after 1.2 s. This is one programmatic cancellation, not a physical Esc test. |
| Adaptive, focus changes to second owned target | 384.835 | First/second controls received 11/89 characters, concatenating to the exact 100-character input. This is one asynchronous focus transition. |

`run.log` contains the first six normal samples and one each of delay/adaptive, cancellation, and switch; `stall.log` contains three alternating baseline/adaptive comparisons under the same artificial delay. The logs include per-request samples and text only from the owned fixtures. `run.sh.txt` and `run-stall.sh.txt` are actual guest-run scripts, with the former setting up and extracting the package and the latter reusing it. To reproduce only in an isolated GNOME Wayland guest, put the candidate AppImage and copies of the four scripts without `.txt` suffix into `/tmp/inkecho-transport-pacing-r1/`, then run `bash run.sh` followed by `bash run-stall.sh`.

The small sample does not prove performance across ordinary workloads; the artificial service pause is not representative of everyday load. In these cases the policy cannot establish target rendering or improve measured correctness, while it increases the stalled sample's total duration by roughly 200 ms. Therefore enabling this heuristic as the requested 40 ms window-frame synchronization would be misleading and could worsen responsiveness. No product changes are proposed without a demonstrable target-specific signal or evidence of a user-visible benefit. The tests do not cover 24.04, other backends, browser/terminal targets, real input, or complete dual-system package validation.
