# Private D-Bus response-sender spoofing regression

This experiment uses `dbus-run-session` to create a disposable D-Bus with three connections in a single synthetic test process: a mock pinned service, a different mock attacker, and an actual InkEcho bridge client. No real desktop service, user application, user text, microphone, cloud service or clipboard is accessed. The mock service and attacker cooperate to know the request serial; this demonstrates the reply-handling flaw, not a complete attack chain or cross-user access. Same-UID processes are not a security boundary. All submitted text is fixed synthetic input.

In the pre-fix Fcitx run, the mock service records delivery of the first character while a different connection sends a matching-serial fake status 3. `fcitx-before.log` shows the actual bridge retried that character and returned `no_target`, accepted zero, uncertainty false and offset zero, which would satisfy the router's zero-prefix fallback guard despite the mock delivery. In the post-fix run, `fcitx-after.log` shows one request and `delivery_unknown`, uncertainty true, no offset; no automatic retry or fallback is justified.

For IBus, the mock trusted-owner verifier is deliberately injected because this private test has no GNOME Shell; it does not test process-identity authentication. Before the fix, a forged `attempted` reply allowed the bridge to send both characters. Afterward, only the first was sent and `delivery_unknown` returned. See `ibus-before.log` and `ibus-after.log`. Companion `*_legit.py.txt` scripts use the pinned service to respond; `fcitx-legit.log` and `ibus-legit.log` show normal synthetic calls still succeed. `daemon-sender.log` separately records the private D-Bus daemon reply sender as `org.freedesktop.DBus` and its matching `GetNameOwner` body.

To reproduce, copy the Python files without `.txt` suffix into a temporary directory, then run each with `dbus-run-session -- env PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=<source-root> <project-python> <probe.py>`, once using the source before the fix and once after. The scripts rely on installed `dbus-next`; they are not ordinary desktop or package tests. Source paths used in the logs were the workspace and a temporary patched copy respectively. No public claim is made about arbitrary D-Bus broker implementations or all operating systems.
