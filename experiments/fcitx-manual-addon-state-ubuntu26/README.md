# Fcitx user addon disable: Ubuntu 26.04 Wayland

The base AppImage SHA-256 `602dab02b4837bb8d30c864dbe50d0413d58d53afb53d9695c7f96f50cdfb756` was verified in the guest. Ubuntu 26.04 GNOME native Wayland used an externally network-isolated KVM container, original and backing disks mounted read-only, and a temporary QEMU snapshot. The test Fcitx process and XDG profile were private; host user credentials were not mounted. No text or clipboard was read or sent.

`manual.log` uses unmodified package code. After install/enable, a private Fcitx service was controlled with the official `org.fcitx.Fcitx.Controller1.SetAddonsState` API. `GetAddonsV2` showed the InkEcho addon enabled field change from true to false, but its already loaded `RuntimeVersion` endpoint remained live and the next `detect_system_framework()` still selected Fcitx. After setting the addon state true, both addon listing and detector returned enabled. This demonstrates that a user-requested addon disable can be ignored by the old auto selection while the library remains loaded. The test changes only the isolated Fcitx configuration and does not claim this was a GUI click.

`fixed.log` reran the same manual state cycle with only `framework_detection.py` overlaid, SHA-256 `119ebfaee65ce6a8b04e3652f9712c7916e57e73c64a37e3b59ac5844555033d`. With the addon enabled detection selected Fcitx; when the control API reported disabled, detection returned null even though RuntimeVersion remained available; on re-enable selection resumed. The fix queries the pinned controller's `GetAddonsV2`, checks response sender and signature, requires exactly one InkEcho row with a true enabled bit, and continues existing owner/version checks. Unknown, malformed or ambiguous status must fail closed. The [Fcitx controller implementation](https://github.com/fcitx/fcitx5/blob/master/src/modules/dbus/dbusmodule.cpp) identifies the enabled field at position 5 in that struct. Test scripts are saved with `.txt` suffix; the fixed runner overlays precisely the one named module.

This is a controlled status check, not a full actual output task or final package acceptance. Checking the state before a task cannot atomically prevent a user toggling it between the check and a subsequent Commit; no claim is made that this closes that in-flight race. IBus behavior and Ubuntu 24 are untested by this experiment. Scripts use a private profile and restore user-manager hints; QMP system_powerdown completed, docker wait returned 0, and the container was removed. To reproduce, copy AppImage and scripts into `/tmp/inkecho-r4-test/`, remove `.txt`, run `bash probes/run.sh 602dab02b4837bb8d30c864dbe50d0413d58d53afb53d9695c7f96f50cdfb756 wayland`, followed by the equivalent `run-fixed.sh` with the overlay in `probes/`, in an isolated GNOME Wayland guest.
