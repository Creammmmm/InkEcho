# Ubuntu 24.04 GNOME X11: explicit IBus candidate

Candidate AppImage `0.10.2` SHA-256 `207b97eb667e5439137b51963a2aa09515c7ba50a83496d9c10070e989252685`, extracted unmodified. Its previously recorded `app.py`, `platform/output_router.py`, and `platform/ibus.py` hashes match current workspace files. Test used synthetic 200-character content, stub recording and local synthetic transcription, and owned GTK controls. User data, clipboard, live microphone and cloud API were not used.

Ubuntu 24.04.5 was run in a network-isolated container using KVM and QEMU `-snapshot`; guest and base images were mounted read-only, as was the input 9p share. Only a dedicated disposable VM SSH key was copied into the temporary container directory, then removed. In the temporary guest layer, the candidate extension was installed in the GNOME user extensions directory and explicitly enabled. `gnome-extensions info` reported `ACTIVE`, session 1 reported active X11 and unlocked, and `ibus engine` was `xkb:us::eng`.

- `ubuntu24-x11-r3.log`: full case captured precisely the 200-character input in the owned TextView, 200 Commit timeout entries, diagnostic `ibus_delivery_unknown`, the message “IBus 已尝试输入，但无法确认目标是否收到；请检查光标位置，未自动重试。”, and outcome `failed`. The sender observed the calls but cannot prove generic target reception; the actual TextView contents provide proof for this owned target only.
- Same log: cancellation after the first received character produced a two-character correct prefix and two Commit timeout entries, then `cancelled`, with no later character observed. The second character may already have been sent when the cancellation signal arrived. This is a single sample.
- `no-target-r2.log`: a separate test focused an owned GTK button rather than a text field (`no_target_focus`, active=true, button focus=true), before sending. Neither TextView received any text; 200 Commit timeout entries occurred and the same uncertainty message and `failed` outcome followed. This verifies this particular non-text control case, not the absence of every IBus virtual context or all applications.

The target probe's `passed` is an old Fcitx-specific assertion and is false even for the observed IBus cases; assess actual JSON fields instead. The first no-target attempt in `ubuntu24-x11-r3.log` is invalid: the X11 activation command timed out and no focus switch was established, so the TextView received the full text. `ubuntu24-x11.log` and `ubuntu24-x11-r2.log` record earlier setup failures (reboot cleared `/tmp`, then a pre-existing mount); no conclusions are drawn from them. `target-focus.py.txt` is the corrected no-target probe. The earlier version is reconstructed as `target-focus-r3-reconstructed.py.txt` by reversing the documented callback change; its original hash was not captured, so it cannot be asserted byte-identical. `prepare-run.sh.txt` and `no-target.sh.txt` document execution (remove the `.txt` suffix when recreating the guest input); running them requires an isolated guest only.

Afterward guest poweroff completed, Docker wait returned 0, the container was removed, and its write layer was discarded. This is a targeted experiment, not full package acceptance. No IBus automatic selection, rapid focus race, actual microphone/API/hotkey, browser/terminal, Ubuntu 26 X11, or complete release gate was tested.
