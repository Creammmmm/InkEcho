# IBus target identity queries: isolated Ubuntu 24.04

This experiment checked existing private-bus identity probes on Ubuntu 24.04.5, IBus `1.5.29-rc2`. An externally network-isolated KVM guest ran on a temporary QEMU snapshot with its original and backing disks mounted read-only. No host user credentials were mounted. Each script started its own `dbus-run-session`, temporary home, runtime directory, IBus daemon and socket, cleaned them on exit, and queried only its own synthetic objects. It did not access the logged-in desktop input method, change its engine, send text, or read surrounding text or queued key-event content.

The `client_pid_probe` positive control successfully resolved its own unique IBus connection name with `GetNameOwner`; `GetConnectionUnixProcessID` on that same private bus returned `org.freedesktop.DBus.Error.UnknownMethod`. The `context_identity_probe` introspected the IBus daemon's fake context and a separate synthetic real context with matching test capabilities: both declared the same three write-only properties and one readable `PostProcessKeyEvent` property. The latter was deliberately not read because its queue may contain text. Queries for `Client`, `ClientName`, `Fake`, and `Capabilities` returned `InvalidArgs` for both. Exact stdout and stderr are preserved.

This extends the previous isolated Ubuntu 26 result to the tested 24.04 IBus implementation. It does not prove all installations lack other identification interfaces, associate an actual desktop control with its input context, or prove delivery. The synthetic real context is a positive control for the query surface, not a desktop GTK application. These results do not justify enabling automatic IBus routing or replaying an attempted commit, and no product patch was made.

To reproduce in a disposable guest, copy both script directories, remove the `.txt` suffixes from `run.sh` and `probe.py`, then run `bash client_pid_probe/run.sh` and `bash context_identity_probe/run.sh`; the scripts themselves create private buses and temporary directories. The guest received QMP system_powerdown, docker wait returned 0, and the temporary container was removed.
