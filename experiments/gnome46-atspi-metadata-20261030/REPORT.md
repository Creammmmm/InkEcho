# GNOME46 AT-SPI composition-metadata negative control

2026-10-30. Released-source baseline16a36b9; isolated parent from actual0.12.0 package24 test, guest Ubuntu24.04.5/GNOME46.0 nativeWayland. Research only: no product candidate or package output acceptance, and no generic accessibility compatibility claim.

Two own GTK3 nativeWayland Entry processes were created sequentially, one GTK_IM_MODULE=simple and one fcitx. Both had actual active/focused GdkWaylandDisplay state and accepted a real VM QMP a press/release before the preedit comparison; their independent actors recorded only PID, focus, backend, synthetic text length, preedit length and key-event count. No user document, accessibility body, clipboard or unknown user key was read. Each QMP request used fresh own PID/cmdline/native active/focus guard, with only fixed a/n/i/Space. Fcitx daemon used a fresh private config/data/cache, not the user's IM profile. No user-manager IM hints or engine settings were changed outside that private daemon.

The actual Pinyin engine produced ni preedit_length2 while synthetic committed text_length0. Before composition and during it, ALL tested AT-SPI fields were equal: interfaces Accessible/Action/Collection/Component/EditableText/Text; focused/editable/sensitive/showing true; caret_offset0; selection_count0. The simple target returned the same metadata. Space completed composition, producing text_length1/preedit0. Actor-groundtruth and AT-SPI metadata are independent observations; the adapter did not query GetText or attempt InsertText.

This proves this metadata set cannot authorize safe automatic insertion when IM composition capability is unknown. It does not prove every future accessibility API lacks composition information, or that Fcitx itself cannot protect its own known context. Fresh focus resolves one old-object problem but does not solve this separate preedit blind spot. No unsafe fallback has been enabled; no uncertain text was replayed.

Two startup fixture failures are retained: Docker rejected missing copied frozen path before creation; the next QEMU failed because its existing9p device still referenced that share. The successful r3 restored the original read-only frozen share and unchanged device topology, with a fresh output directory and container name. Its original boot then waited about2minutes for networkd-wait-online, without network relaxation/restart.
